DevSecOps et detection-as-code :
la même discipline, deux surfaces de sécurité

Tu sécurises la chaîne qui produit le cloud et tu utilises cette chaîne pour livrer les détections. Le lab fournit une règle Bicep complète, son KQL et un exemple GitHub Actions avec fédération d'identité.

Théorie : 4 hLab : 7 hRestitution : 3 h

1. Cinq contrôles complémentaires

SurfaceContrôleCe qu'il ne prouve pas
SecretsSecret scanning, push protection, rotationUn faux secret arbitraire n'est pas forcément reconnu ; un secret supprimé du code reste à révoquer
DépendancesInventaire, lockfile, analyse de vulnérabilitésPas une garantie d'absence de paquet malveillant
CodeSAST/CodeQL, revue, testsPas une preuve d'exploitabilité ni de sécurité globale
IaCCompilation, analyse de configuration, policyCompilation réussie ≠ configuration sûre
ImagesScan, provenance et digestImage scannée ≠ image effectivement déployée

La protection de la chaîne comprend aussi les branches, les workflows, les runners et les identités. Une pull request externe ne doit pas obtenir les droits de déploiement. Un runner persistant peut conserver un état compromis entre deux builds ; sa provenance et son nettoyage font partie du modèle de menace.

Defender for Cloud DevOps security peut rassembler les findings des forges prises en charge. Les capacités dépendent du connecteur, de la licence et des analyses réellement exécutées. Relier une image à son dépôt exige des métadonnées de provenance cohérentes ; connecter la forge ne crée pas automatiquement toutes ces relations.

2. OIDC retire un secret, pas la nécessité de contrôler l'accès

Avec la fédération d'identité, le fournisseur de CI émet un jeton de courte durée portant des revendications. Entra accepte le jeton uniquement si la relation fédérée correspond, puis délivre l'accès autorisé au principal. Le contrôle porte sur l'émetteur, l'audience et le sujet : dépôt, branche ou environnement selon le fournisseur.

Dans GitHub Actions, id-token: write autorise la demande du jeton OIDC, pas l'écriture arbitraire dans Azure. Les droits réels sont ceux du principal Entra. Le sujet repo:ORG/REPO:environment:secops-lab doit correspondre à l'environnement référencé dans le job. Les règles de cet environnement et les restrictions de branche protègent cette relation de confiance.

Donne à l'identité uniquement les opérations de déploiement nécessaires. Créer une attribution RBAC demande des privilèges différents de déployer une règle Sentinel. Le template fourni ne crée aucune attribution ; le provisionnement des droits de la CI reste une étape distincte à documenter.

3. Un identifiant stable, un format réellement déployable

Le dépôt doit contenir requête, ressource déployable, paramètres d'environnement, tests et fiche de triage. Un YAML de règle du dépôt communautaire Sentinel n'est pas nécessairement un template ARM/Bicep directement déployable par Repositories : il faut utiliser le format pris en charge ou le convertir.

Contenu fourni dans labs/detection-as-code/
main.bicep                     # analytics rule complète, désactivée par défaut
queries/role-assignment.kql     # logique du chapitre 05
workflow.yml.example            # CI et déploiement manuel OIDC

Le GUID de règle est stable : changer la description met à jour la même ressource. Générer un nouveau GUID à chaque build crée des doublons. Les paramètres portent le workspace et l'état d'activation, pas une copie divergente du code par client.

Repositories : comprendre le comportement réel

Repositories déploie le contenu depuis GitHub ou Azure DevOps. Les smart deployments sont activés par défaut sur les nouvelles connexions et ne redéploient que le contenu modifié. Une modification manuelle au portail n'est donc pas nécessairement écrasée au prochain commit sans rapport. Une suppression du fichier Git ne supprime pas automatiquement la ressource dans Sentinel.

Le dépôt est la source de vérité souhaitée ; la détection de dérive et la suppression contrôlée sont à concevoir. Exporter l'état déployé, comparer les propriétés pertinentes et décider du traitement de la dérive évite de confondre synchronisation et réconciliation complète.

Custom detections as-code

Le support Repositories est documenté en preview avec l'extension MicrosoftSecurity et la ressource Microsoft.Security/detectionRules@2026-06-01-preview. Ce n'est pas le même fournisseur que Microsoft.SecurityInsights/alertRules. L'extension requiert son bicepconfig et un ID de règle ; les custom details et certaines fréquences ont des limitations de preview. Le lab principal utilise une analytics rule standard pour rendre le déploiement et la recette explicites.

4. Quatre niveaux de validation

  1. Structure : compilation Bicep et formats des fichiers.
  2. Sémantique : requête KQL compilable sur le schéma de la cible.
  3. Logique : cas positifs, négatifs, limites, retards et doublons.
  4. Intégration : déploiement, exécution, alerte, entités et réponse.

La compilation Bicep ne lit pas le sens du KQL chargé comme chaîne. Un pipeline vert peut donc déployer une requête qui ne fonctionne pas. Les tests synthétiques ne prouvent pas non plus la présence de la table réelle. Conserve les résultats de chaque niveau avec le commit testé.

Le rollback consiste à redéployer la version précédente avec le même ID et les paramètres appropriés, puis à refaire le test de santé. Il ne retire pas automatiquement les alertes déjà créées et ne révoque pas les actions déjà exécutées. Pour un incident de bruit, la désactivation temporaire est une opération distincte et tracée.

Lab guidé — du fichier à la règle déployée

7 h · dépôt de lab, Azure CLI et workspace Sentinel

Copie main.bicep, le dossier queries/ et workflow.yml.example dans un dépôt dédié. Le workspace doit déjà exister, Sentinel être activé et AzureActivity alimentée.

Comprendre et compiler · 45 min

Portail Azure (GUI)

La version ARM main.json fournie est compilée depuis le main.bicep du cours. Ce volet permet d'inspecter ce résultat dans le portail. Pour pratiquer la compilation Bicep elle-même et provoquer une erreur de compilation, utilise le volet CLI.

  1. Télécharge main.json puis recherche dans Azure Déployer un modèle personnalisé.
  2. Choisis Créer votre propre modèle dans l'éditeur › Charger un fichier et sélectionne main.json.
  3. Repère la ressource Microsoft.SecurityInsights/alertRules, son type Scheduled, le paramètre ruleId stable, les périodes PT5M/PT20M, la requête et le mapping.
  4. Vérifie que enabled est faux par défaut ; clique Enregistrer. Le déploiement est traité en étape 3.
Résultat attenduTu peux expliquer chaque propriété du modèle chargé. Ce chargement n'a créé aucune règle et ne valide pas l'exécution KQL.
Azure CLI / Cloud Shell

Lis chaque propriété du template. Identifie ID stable, scope, fréquence, période, seuil, détails et mapping. Depuis le dossier contenant main.bicep :

Azure CLI · compilation locale
az bicep build --file main.bicep --stdout

Cette commande ne déploie aucune ressource. Le résultat ARM doit contenir une ressource Scheduled avec enabled=false par défaut et le KQL chargé depuis le fichier. Change temporairement un nom de propriété pour observer une erreur, puis restaure-le. Si tu veux reprendre au portail, génère le JSON de ta version avec az bicep build --file main.bicep --outfile main.json.

Valider le KQL dans la cible · 60 min

Azure CLI / Cloud Shell

Depuis le dossier detection-as-code copié dans ton dépôt, renseigne RG et LAW avec les valeurs du workspace cible.

Azure CLI · exécuter le fichier KQL dans la cible
export LAW_GUID=$(az monitor log-analytics workspace show -g "$RG" -n "$LAW" --query customerId -o tsv)
az extension add --name log-analytics
az monitor log-analytics query --workspace "$LAW_GUID" \
  --analytics-query "$(cat queries/role-assignment.kql)" --timespan PT20M --output json

Vérifie le schéma même si la requête ne renvoie rien ; rejoue ensuite le témoin RBAC du chapitre 05 et conserve la preuve de recette.

Portail Azure (GUI)
Portail Azure › Log Analytics › workspace cible › Journaux › mode KQL

Ouvre le fichier KQL, copie sa requête dans l'éditeur puis clique Exécuter. Une sortie vide est plausible sans attribution récente ; vérifie séparément la présence d'AzureActivity et ses colonnes. Rejoue le cas positif du chapitre 05. Conserve le résultat de recette avant de poursuivre.

Déployer désactivé, inspecter puis activer · 75 min

Portail Azure (GUI)
Azure › Déployer un modèle personnalisé › éditeur › charger main.json › Enregistrer
  1. Sélectionne l'abonnement et le groupe de ressources du workspace existant.
  2. Renseigne workspaceName avec son nom exact. Garde ruleId inchangé et enabled = false.
  3. Choisis Vérifier + créer › Créer, puis consulte l'état et les sorties dans RG › Déploiements.
  4. Dans Defender › Microsoft Sentinel › Analytics, retrouve LAB - Attribution de rôle Azure réussie, compare son ID, sa requête, son mapping et son état désactivé.
  5. Une fois la recette KQL de l'étape 2 faite, charge à nouveau le même template avec le même ruleId et enabled = true. Vérifie l'activation, puis réalise l'attribution Reader témoin du chapitre 05.

La validation du formulaire n'est pas un diff what-if. Pour exercer aussi cette capacité, utilise la commande CLI. Si tu changes le Bicep/KQL dans le dépôt, recompile le JSON avant de le charger ; le fichier fourni correspond à la version du cours.

Azure CLI / Cloud Shell

Renseigne RG et LAW avec le groupe du workspace et son nom. Vérifie le contexte d'abonnement, puis prévisualise :

Azure CLI · preview et déploiement sur le lab
az account show --query '{subscription:id,tenant:tenantId,name:name}'
az deployment group what-if --resource-group "$RG" \
  --template-file main.bicep --parameters workspaceName="$LAW" enabled=false
az deployment group create --resource-group "$RG" \
  --template-file main.bicep --parameters workspaceName="$LAW" enabled=false

Dans Analytics, retrouve la règle par son nom et son ID. Compare la requête. Quand la recette est prête, redéploie avec enabled=true et génère une attribution Reader de test. Relève événement, alerte et incident, puis retire l'attribution.

Installer la CI et la fédération · 90 min

Copie workflow.yml.example dans .github/workflows/detections.yml. Crée l'environnement GitHub secops-lab et ses variables AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID, RESOURCE_GROUP et WORKSPACE. Configure la relation fédérée de l'application Entra avec l'émetteur GitHub, l'audience api://AzureADTokenExchange et le sujet de ton dépôt/environnement. Accorde les droits de déploiement sur le périmètre de lab.

Ouvre une PR : seul le build doit s'exécuter. Le job de déploiement fourni est volontairement déclenché par workflow_dispatch sur main ; il déploie désactivé pour rendre l'activation observable. Documente ensuite comment ajouter un déploiement sur merge après recette. Les versions majeures des actions rendent l'exemple lisible ; dans un dépôt durci, épingle les actions à des commits vérifiés et maintenus.

Tester dérive et rollback · 75 min

Modifie la description dans le portail, puis redéploie le template complet : elle doit revenir à la version du dépôt. Si tu utilises Repositories, teste séparément un commit sans changement de la règle puis un commit qui la modifie : les smart deployments expliquent la différence. Reviens à la version précédente par Git et redéploie le même ID.

Observer la forge et livrer · 75 min

Dans l'audit de la forge, retrouve une modification de protection ou de workflow effectuée sur le lab. Relie acteur, commit, PR et exécution de pipeline. Si un connecteur Sentinel est disponible, retrouve le même événement dans sa table ; ne suppose pas le schéma avant inspection. Rends la PR, le build, le déploiement, la recette et le rollback. Désactive la règle de lab et retire la fédération/les droits de la CI si le dépôt n'est plus utilisé.

Validation et corrigés

Le build est vert mais la règle ne fonctionne pas : où regarder ?

Le template peut compiler avec une chaîne KQL invalide. Vérifie le schéma et les permissions de la cible, la requête enregistrée, le scope, l'activation et l'état de planification. Compare ensuite les événements réellement reçus au contrat de détection. Garde des contrôles séparés pour compilation, logique et intégration.

Supprimer le fichier Git retire-t-il la règle ?

Non dans le comportement Repositories documenté. Il faut une procédure de retrait qui supprime ou désactive la ressource cible et évite son redéploiement. Vérifie l'absence dans le portail et les dépendances de playbook, de reporting et de documentation.

À démontrer
  • Une règle Bicep compilée puis déployée avec un ID stable.
  • Une identité OIDC au sujet et au scope expliqués.
  • Une PR sans droit de déploiement et une exécution autorisée séparée.
  • Un vrai test KQL et une recette événement→alerte.
  • Un rollback et un comportement de dérive observés.
