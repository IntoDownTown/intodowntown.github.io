Socle Azure :
comprendre le modèle avant de le défendre

Avant de collecter un journal ou d'écrire une détection, il faut savoir qui agit, sur quoi, et par quel plan. Ce socle décrit la hiérarchie des ressources, la séparation control plane / data plane, la différence entre Entra ID et Azure RBAC, et le rôle central des jetons. Chaque notion est rattachée à la trace qu'elle laisse, car c'est cette trace que le reste du cours exploite.

Théorie : 5 hLab : 2 hRestitution : 1 h

1. La hiérarchie des ressources et le rôle d'ARM

Azure organise tout en une arborescence : un tenant Entra ID héberge un ou plusieurs management groups, qui contiennent des subscriptions (unité de facturation et de quota), elles-mêmes découpées en resource groups, qui contiennent les ressources (une VM, un Key Vault, un workspace). Un héritage descend le long de cet arbre : une attribution de rôle ou une policy posée sur un management group s'applique à tout ce qui est en dessous. Comprendre ce sens d'héritage est la base du raisonnement sur les droits et sur l'exposition.

Toute opération de gestion passe par Azure Resource Manager (ARM), l'API unique exposée sur management.azure.com. Que tu utilises le portail, Azure CLI, Azure PowerShell ou Terraform, la requête finit en appel REST authentifié vers ARM. Chaque ressource a un identifiant canonique, le resourceId, de la forme /subscriptions/<id>/resourceGroups/<rg>/providers/<provider>/<type>/<nom>. Ce chemin est la clé de jointure que tu retrouveras dans presque toutes les requêtes KQL du cours : il relie une alerte, un propriétaire RBAC et un scope de policy au même objet.

RepèreUn resourceId n'est pas un détail d'affichage : c'est l'ancre qui corrèle journaux, droits et politiques. Préserve-le partout où tu enrichis une alerte.

2. Control plane et data plane : deux portes distinctes

Azure sépare deux plans qui ne s'authentifient pas forcément de la même façon et ne produisent pas les mêmes journaux. Le control plane gère le cycle de vie des ressources : créer une VM, attribuer un rôle, ouvrir une règle réseau. Il passe par ARM et sa trace est Azure Activity Log. Le data plane manipule le contenu : lire un secret dans un Key Vault, écrire un blob, interroger une base. Sa trace est propre à chaque service, via ses diagnostic settings.

La conséquence défensive est directe : voir une attribution de rôle dans l'Activity Log prouve que le droit a été donné, pas qu'il a été utilisé. L'usage réel vit dans le data plane, qui est muet si ses diagnostic settings ne sont pas configurés. Beaucoup d'enquêtes échouent non par absence d'attaque mais par absence de collecte côté données. Le chapitre 01 reviendra sur l'activation systématique de ces journaux ; retiens ici qu'une détection control plane et une détection data plane répondent à deux questions différentes.

3. Entra ID n'est pas Azure RBAC

C'est la confusion la plus coûteuse pour un débutant. Entra ID (ex-Azure AD) est l'annuaire d'identité : il gère utilisateurs, groupes, applications et service principals, et ses rôles d'annuaire (Global Administrator, Privileged Role Administrator…) pilotent le tenant et Microsoft 365. Azure RBAC gère l'accès aux ressources Azure (Owner, Contributor, Reader…) le long de la hiérarchie vue au §1. Ce sont deux systèmes d'autorisation distincts, avec deux journaux distincts : AuditLogs pour Entra, AzureActivity pour Azure RBAC.

Les deux mondes communiquent par des ponts qu'il faut connaître car ce sont des voies d'escalade. Un Global Administrator peut activer « Access management for Azure resources » (elevate access) et obtenir User Access Administrator à la racine de toutes les subscriptions. Un groupe Entra utilisé dans une attribution Azure RBAC transforme une modification d'appartenance (côté AuditLogs) en gain de droits sur les ressources (visible côté AzureActivity seulement par l'attribution initiale). Une application avec un credential ajouté peut agir sur Azure selon ses attributions. Comprendre ces ponts, c'est comprendre pourquoi une enquête doit souvent croiser les deux journaux.

À retenirUn rôle Entra puissant ne donne pas automatiquement accès aux données des ressources, et un Owner de subscription n'est pas administrateur du tenant. Mais les ponts entre les deux rendent chaque frontière franchissable : la surveillance porte sur les ponts, pas seulement sur les rôles.

4. Tout repose sur des jetons

Azure et Entra sont OAuth 2.0 / OpenID Connect. Une identité ne « se connecte » pas à une ressource : elle obtient un jeton auprès d'Entra, puis le présente à une API. Trois types comptent. L'access token est de courte durée (environ une heure), signé, et porte des revendications : qui (oid, upn), pour quelle audience (aud, l'API visée), avec quelles permissions (scopes/roles). Le refresh token, plus durable, sert à obtenir de nouveaux access tokens sans réauthentification. L'ID token prouve l'identité à l'application.

Charge utile simplifiée d'un access token (revendications clés)
{
  "aud": "https://management.azure.com/",   // l'audience : ARM, ici le control plane
  "iss": "https://sts.windows.net/<tenantId>/",
  "oid": "<objectId de l'identité>",        // stable, meilleur pivot que l'UPN
  "upn": "analyste@contoso.com",
  "scp": "user_impersonation",               // scopes délégués (flux utilisateur)
  "roles": ["..."],                          // app roles (flux application)
  "exp": 1730000000                          // expiration courte
}

Deux idées défensives en découlent. D'abord l'audience cloisonne : un jeton pour Microsoft Graph ne vaut rien contre ARM, et inversement. Un acteur qui veut agir sur plusieurs plans doit obtenir plusieurs jetons, ce qui multiplie les traces de requêtes de jeton. Ensuite, un jeton volé reste valable jusqu'à son expiration même si le mot de passe change : seule la révocation de session/refresh token et le Continuous Access Evaluation coupent court. C'est pourquoi le vol de jeton (et de refresh token) est au cœur des attaques cloud modernes, et pourquoi les signaux de connexion (SignInLogs) et les anomalies de device/IP comptent autant que le mot de passe.

Côté identité pour les revendications : préfère toujours l'oid (objectId, stable) à l'UPN (modifiable) comme clé de corrélation, et distingue un utilisateur d'un service principal — ne range jamais un GUID de service principal dans un champ UPN, rappel déjà posé au chapitre 05.

5. Identités managées : du secret au jeton automatique

Plutôt que de stocker un secret dans une VM ou une fonction, Azure propose l'identité managée (managed identity) : la ressource se voit attribuer une identité Entra et obtient des jetons automatiquement, sans credential à gérer. C'est une excellente pratique de sécurité — moins de secrets exposés — mais c'est aussi un élément central du socle car cette commodité devient un chemin de pivot si la ressource est compromise.

Le mécanisme : depuis l'intérieur de la ressource, le code appelle l'IMDS (Instance Metadata Service, une adresse de lien local non routable) pour recevoir un access token correspondant à l'identité managée, pour l'audience demandée. Les droits de ce jeton sont exactement les attributions Azure RBAC de l'identité managée. Une identité managée « Contributor » sur un resource group donne donc à qui exécute du code dans la ressource les mêmes droits — sans jamais manipuler de mot de passe.

Lien avec la suiteDeux types : system-assigned (liée au cycle de vie d'une ressource) et user-assigned (autonome, attachable à plusieurs ressources). La partie pentest du cours montre comment un accès à la ressource se transforme en jeton d'identité managée, et le socle explique pourquoi : le jeton suit les droits RBAC, pas l'utilisateur humain.

Principe de moindre privilège appliqué : une identité managée ne doit porter que le scope et le rôle strictement nécessaires. Un « Contributor » à l'échelle de la subscription posé par confort sur une petite fonction est une dette de sécurité majeure, car il définit le rayon d'un pivot éventuel.

Dessiner la hiérarchie · 30 min

Portail › Management groups, puis Subscriptions

Note l'arbre management group → subscription → resource groups. Pour une ressource, copie son resourceId complet et décompose chaque segment. Tu dois pouvoir dire, pour une attribution donnée, jusqu'où elle hérite.

Séparer les deux plans · 30 min

Choisis un Key Vault. Dans « Access control (IAM) », relève les attributions RBAC (control plane). Dans « Diagnostic settings », vérifie si les journaux data plane sont envoyés quelque part. Conclus : saurais-tu dire qui a lu un secret hier ? Si non, c'est un angle mort à documenter.

AttenduUne phrase par plan : où est la trace, et est-elle réellement collectée.

Distinguer Entra et Azure RBAC · 30 min

Dans Entra ID › Roles and administrators, liste les rôles d'annuaire attribués. Dans une subscription › IAM, liste les rôles Azure. Identifie une identité présente des deux côtés et explique ce que chaque rôle lui permet — et ce qu'il ne lui permet pas.

Lire un vrai jeton · 30 min

Azure CLI · obtenir et inspecter un access token (lab)
az account get-access-token --resource https://management.azure.com \
  --query accessToken -o tsv
# Colle la valeur sur jwt.ms (outil Microsoft) et lis aud, oid, exp, scp.

Vérifie l'audience, l'objectId et l'expiration. Demande ensuite un jeton pour https://graph.microsoft.com et compare : même identité, audience différente, donc jeton différent. Ne partage jamais un jeton réel ; révoque la session si besoin.

Validation et corrigés

J'ai Owner sur une subscription : suis-je administrateur du tenant ?

Non. Owner est un rôle Azure RBAC : il porte sur les ressources de son scope. L'administration du tenant (identités, Conditional Access) relève des rôles d'annuaire Entra. Les deux ne se recouvrent que via des ponts explicites, comme elevate access d'un Global Administrator.

Une attribution de rôle est dans l'Activity Log : l'accès a-t-il été utilisé ?

Rien ne le prouve. L'Activity Log (control plane) montre que le droit a été donné. L'usage réel vit dans le data plane du service concerné et n'apparaît que si ses diagnostic settings sont activés. Deux questions, deux journaux.

On a réinitialisé le mot de passe du compte compromis : est-ce terminé ?

Pas forcément. Un access token déjà émis reste valable jusqu'à son expiration, et un refresh token volé peut régénérer des jetons. Il faut révoquer les sessions/refresh tokens et s'appuyer sur Continuous Access Evaluation, pas seulement changer le mot de passe.

À démontrer
  • L'arbre tenant → ressource et le sens de l'héritage des droits.
  • La différence control plane / data plane sur un exemple réel et son journal.
  • La distinction Entra ID / Azure RBAC et au moins un pont entre eux.
  • La lecture d'un access token : audience, objectId, expiration.
  • Pourquoi une identité managée relie des droits RBAC à l'exécution de code.
